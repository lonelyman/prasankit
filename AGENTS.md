## Backend Composition Rule

- `app-api/internal/bootstrap` is the composition root.
- Keep the composition root small during Foundation. Do not add placeholder repositories, services, handlers, mailer, storage, or auth wiring before the real module is being implemented.
- When a module is implemented, wire in this order: config → infrastructure clients → repositories → services/use cases → HTTP handlers → router.
- `App` must own long-lived resources that need shutdown (PostgreSQL, Redis, MinIO clients, worker pools, the Fiber server) and close each in graceful shutdown.
- GORM is for query/ORM only. Do not let GORM auto-migrate production schema. Schema is managed by SQL migrations under `app-api/database/migrations/` via goose.
- Primary keys use UUID v7 generated by the Go application. New tables use PostgreSQL `UUID` columns but must not rely on database-side `gen_random_uuid()` defaults.
- Auth remains Session-based + Redis + httpOnly Cookie. Do not introduce JWT as the primary auth strategy.
- Auth identity is separated from user account: `user_accounts` is the account owner; `auth_identities` stores login methods (email/password and future OAuth providers).

## Per-Handler Auth/Tenant/Permission Pattern

There is **no shared middleware** for auth, tenant, or permission. Each HTTP handler defines its own `requireSession`, `requireTenantContext`, and `requireWorkspacePermission(perm)` methods and applies them per route. When adding a new module, copy the pattern from `workspacehttp` / `projecthttp` / `taskhttp`. Do not extract a shared middleware without explicit user approval — it touches every route.

## Review Checklist

- Is `tenant_id` resolved by backend context?
- Is `tenant_id` absent from Workspace API URLs?
- Do workspace/project queries filter by `tenant_id`?
- Are permissions enforced by backend?
- Is `/api/v1` used consistently?
- Does success response use root key `data`? Error use `error`?
- Do list responses use `data.items` and `data.pagination`?
- Do list APIs have pagination?
- Are file URLs stored or exposed incorrectly?
- Does file access use a signed URL gated by a backend permission check?
- Are sensitive values logged?
- Are activity logs written for important actions?
- Are security events written for auth/security actions?
- Is auth identity separated from user account (not treating email as the only identity source)?
- Are soft deletes used correctly?
- Are unique constraints compatible with soft delete?
- Are new primary keys generated as UUID v7 by the application?
