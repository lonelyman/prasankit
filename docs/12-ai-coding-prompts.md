## 12.2 Prompt Header

แปะ block นี้ก่อนสั่ง AI ทุกครั้ง (เป็นชั้นกันพลาดที่ดีที่สุดเพราะแปะไปกับ prompt ตรง ๆ)

```text
Context Guard:
You are working on Prasankit (multi-tenant project/workspace management platform).

Stack: Next.js + TypeScript / Go Fiber + GORM / PostgreSQL / Redis / MinIO / Docker Compose

Hard Rules:
- tenant_id must come from backend Tenant Context only.
- Do not put tenant_id in Workspace API URL.
- API prefix must be /api/v1.
- Success response root key is data. Error root key is error.
- List response uses data.items and data.pagination.
- Every list API must have pagination.
- File records must not store full URL. Store bucket_key + object_key only.
- File access must use backend permission check + signed URL.
- Every Workspace/Project API must pass Permission Guard.
- Auth uses Session-based Auth + Redis + httpOnly Cookie (no JWT as primary).
- Primary keys are UUID v7 generated by the Go application.
- Do not add out-of-scope features (Finance/Deliverable/Notification/Reports are NOT MVP-0).
```

## 12.3 Global Coding Prompt

```text
You are helping build Prasankit, a multi-tenant project/workspace management platform.

Stack:
- Frontend: Next.js + TypeScript
- Backend: Go + Fiber + GORM
- PostgreSQL, Redis, MinIO, Docker Compose

Follow these architecture rules:
- Shared database + tenant_id.
- tenant_id resolved by backend Tenant Context (never accept from frontend).
- Workspace API must not include tenant_id in URL.
- API prefix /api/v1.
- Success response uses root key data. Error uses error. List uses data.items + data.pagination.
- All Workspace/Project endpoints pass Permission Guard.
- Important actions write Activity Log or Security Event.
- File records store bucket_key + object_key only — no full URL.
- File access goes through backend permission check + signed URL.
- All list APIs paginate.
- Avoid LIKE '%keyword%' on large tables without justification.
- Soft delete for important business entities. Unique constraints consider soft delete.
- Do not introduce out-of-scope features.

When coding:
1. Explain the intended change briefly.
2. Show files to create/update.
3. Provide code in complete usable form.
4. Include validation and error handling.
5. Keep naming consistent with Prasankit.
6. Do not change architecture unless explicitly asked.
```

## 12.4 Backend Prompt

```text
You are implementing backend code for Prasankit.

Stack: Go + Fiber + GORM + PostgreSQL + Redis + MinIO

Architecture (Pragmatic Hexagonal):
- internal/transport/http/{m}http — handler: parse/format only.
- internal/modules/{m}/{m}svc — service: business logic.
- internal/modules/{m} — domain entity + repository interface.
- internal/adapters/database/postgres/{m}repo — GORM repository implementation.
- internal/transport/http/presenter — response envelope.
- No shared auth/tenant/permission middleware — each handler implements its own requireSession / requireTenantContext / requireWorkspacePermission methods. Copy the pattern from workspacehttp/projecthttp/taskhttp.

API rules:
- Prefix /api/v1.
- Workspace API path must not contain tenant_id.
- tenant_id comes from Tenant Context resolved via X-Workspace-Slug header.
- Every workspace/project query must include tenant_id.
- Never query project_id, task_id, file_id alone without tenant_id.
- Success response root key = data. List = data.items + data.pagination. Error = error.

Security rules:
- Validate session from httpOnly Cookie / Redis session store.
- Check user account status (active).
- Check active workspace membership and permission.
- Do not log secrets, session tokens, or signed URLs.
- Write activity logs for business actions; security_events for security actions.
- Generate UUID v7 IDs and set timestamps in Go before insert.

Task:
Implement [FEATURE_NAME].

Required output:
1. Route definitions (per-handler middleware methods).
2. Handler with request/response structs.
3. Service.
4. Repository (interface + GORM impl).
5. Validation and error handling.
6. Activity/security log where needed.
7. Migration notes if schema changes.
```

## 12.5 Frontend Prompt

```text
You are implementing frontend code for Prasankit.

Stack: Next.js + TypeScript + App Router + Tailwind CSS

UI contexts (do not mix):
1. Public App Template
2. Owner / Business Admin Template
3. Workspace Portal Template
4. Project Detail Template
5. Platform Admin Template

Rules:
- Keep visual context clear (header label, sidebar, breadcrumb, badge).
- Workspace Portal must clearly show current workspace; Project Detail must show current project.
- All data visibility depends on role/permission from backend. Do not trust frontend-only permission checks.
- API success root is data. Error root is error. List uses data.items + data.pagination.
- Do not hardcode tenant_id.
- Local dev tenant path: /w/:slug. Production/demo: subdomain.
- File open must call backend download-url endpoint — never use stored public URL.

Task:
Build [PAGE_OR_COMPONENT_NAME].

Required output:
1. Route structure.
2. Component structure.
3. TypeScript types.
4. API client function.
5. Loading / error / empty state.
6. Permission-aware UI behavior.
7. Responsive layout.
```

## 12.6 Database Migration Prompt

```text
You are creating database migrations for Prasankit.

Database: PostgreSQL, shared database + tenant_id, goose migrations under app-api/database/migrations/.

Rules:
- UUID v7 primary keys generated by the Go application.
- Use PostgreSQL UUID columns; do not add gen_random_uuid() defaults for primary keys.
- Workspace data tables include tenant_id. Project data tables include tenant_id + workspace_id + project_id.
- Important tables include audit fields. Use soft delete for important business data.
- Unique constraints consider soft delete. Use partial unique index WHERE deleted_at IS NULL where reuse is allowed.
- Add indexes for tenant_id + common filters; add indexes for join columns.
- Use child tables for optional/multi-value/history data rather than bloating main tables.
- Do not store full file URL. Store bucket_key + object_key only.

Required output:
1. Migration SQL (Up + Down).
2. Indexes, constraints, soft-delete considerations.
3. Notes about high-volume tables.
```

## 12.7 Docker / Deploy Prompt

```text
You are writing Docker/deploy configuration for Prasankit.

Service names: prasankit-web, prasankit-api, prasankit-pgsql, prasankit-redis, prasankit-minio, prasankit-proxy.

Rules:
- Docker Compose for MVP/Demo.
- Bind mount or well-defined volumes for data safety. Important data must not live only in container layer.
- PostgreSQL and MinIO data paths must be persistent.
- Do not use `docker compose down -v` or `docker system prune --volumes` in demo/production.
- Use .env for secrets/config. Do not commit real secrets.
- Healthcheck for pgsql, redis, minio. API depends on healthy infra; web depends on API.
- Use deploy script to reduce manual command mistakes.

Generate:
1. docker-compose.yml
2. .env.example
3. deploy.sh
4. backup script skeleton
5. notes for data safety
```

## 12.8 Review Prompt

```text
Review the current implementation of Prasankit.

Check:
- Is tenant_id resolved by backend context? Absent from Workspace API URL?
- Do workspace/project queries filter by tenant_id?
- Are permissions enforced by backend?
- Is /api/v1 used consistently?
- Does success response use data? Error use error? List use data.items + data.pagination?
- Do list APIs have pagination?
- Are file URLs stored or exposed incorrectly? Does file access use signed URL?
- Are sensitive values logged?
- Are activity logs written for important actions? Security events for auth/security actions?
- Are soft deletes used correctly? Unique constraints compatible with soft delete?
- Are indexes adequate?
- Are dangerous docker commands avoided? Backups documented?

Return:
1. Pass/fail summary.
2. Critical / Medium / Minor issues.
3. Recommended fixes.
4. Files likely affected.
```

## 12.10 Module Prompt Examples

### Project Module

```text
Implement Project module for Prasankit.

Scope: list/create/get/update/archive/restore project; project members; project settings.

Rules:
- Endpoint under /api/v1/workspace/projects.
- No tenant_id in URL. tenant_id from Tenant Context. Every query uses tenant_id.
- project_id must always be paired with tenant_id.
- Create Project must add creator as Project Owner.
- Project must have at least one Project Owner.
- Project code follows workspace policy.
- Soft delete/archive. Activity logs. Paginated lists.
```

### Task Module

```text
Implement Task module for Prasankit.

Scope: list/create/get/update/delete task; change status; reassign; watchers; checklist; comments; attachments as file relation.

Rules:
- Endpoint under /api/v1/workspace/projects/{project_id}/tasks.
- No tenant_id in URL. tenant_id from Tenant Context.
- Query by tenant_id + project_id + task_id.
- Validate assignee is active project member.
- Reassign writes task_reassign_logs.
- Attachments link to Project File Center (relation, not copy).
- Activity logs. Paginated lists.
```

### File Module

```text
Implement Document/File module for Prasankit.

Scope: folder tree; file list; upload request; complete upload; download signed URL; metadata update; soft delete/restore; external link; file relations.

Rules:
- Do not store full URL. Store bucket_key + object_key.
- Client must not generate object_key.
- Backend validates permission before upload/download.
- Backend returns signed URL with expiration. Do not log signed URL.
- Delete from UI = soft delete. Object hard delete only via cleanup policy.
- Attachment = relation, not copy.
```
