# Auth Flow Status

เอกสารนี้ใช้บอกสถานะจริงของ Auth flow ว่าทำอะไรไปแล้ว อะไรยังเป็น manual/testing workaround และจุดไหนต้องกลับมาแก้เมื่อเริ่ม frontend หรือ workspace flow

## Current Status

ตอนนี้ทำ backend foundation ของ email/password auth แล้วบางส่วน:

```text
register backend done
-> send verification email done
-> verify-email backend done
-> frontend verification page not done
-> resend verification email not done
-> login/session not done
```

## What Is Done

### POST /api/v1/auth/register

ทำแล้ว:

- รับ email/password
- normalize email
- validate email
- validate password ขั้นต่ำ 8 ตัวอักษร
- เช็ก email ซ้ำ
- rate limit การส่ง verification email ต่อ IP ด้วย Redis
- hash password ด้วย bcrypt
- สร้าง `user_accounts`
- สร้าง `auth_identities`
- สร้าง `auth_email_verification_tokens`
- เก็บเฉพาะ token hash ใน database
- ส่ง verification email ผ่าน SMTP จริง
- เขียน `security_events`:
  - `auth.account_registered`
  - `auth.email_verification_sent`

ผลลัพธ์ปัจจุบัน:

- account ใหม่เป็น `pending_verification`
- email มี frontend URL ตาม `MAIL_VERIFY_BASE_URL`
- link ใน email ควรเป็น frontend URL เช่น:

```text
http://localhost:3000/auth/verify-email?token=<token>
```

### POST /api/v1/auth/verify-email

ทำแล้ว:

- รับ `token`
- hash token แล้วหาใน `auth_email_verification_tokens`
- เช็ก token status เป็น `active`
- เช็ก token ยังไม่หมดอายุ
- mark token เป็น `used`
- set `auth_identities.email_verified_at`
- set `user_accounts.status = active`
- เขียน `security_events`:
  - `auth.email_verified`

ผลลัพธ์ปัจจุบัน:

- ถ้า token ถูกต้อง account เปลี่ยนเป็น `active`
- token ใช้ซ้ำไม่ได้
- token หมดอายุได้ตาม `MAIL_VERIFY_TOKEN_TTL`

## What Is Temporary

ตอนนี้ยังไม่มี frontend page:

```text
/auth/verify-email
```

ดังนั้นการทดสอบตอนนี้ยังเป็น manual:

1. สมัครด้วย `POST /api/v1/auth/register`
2. เปิด email ที่ได้รับ
3. copy ค่า `token` จาก query string ใน link
4. ยิง `POST /api/v1/auth/verify-email` ด้วย curl

นี่เป็น temporary testing flow เท่านั้น ไม่ใช่ user flow สุดท้าย

## Correct Final User Flow

Flow ที่ต้องเป็นจริงเมื่อมี frontend:

```text
User opens register page
-> frontend calls POST /api/v1/auth/register
-> backend sends verification email with frontend URL
-> user clicks email link
-> frontend opens /auth/verify-email?token=...
-> frontend shows verifying state
-> frontend calls POST /api/v1/auth/verify-email
-> frontend handles success/error states
-> user continues to login or workspace setup
```

Backend ไม่ควรเป็นคน render หน้า verify email เองใน architecture ปัจจุบัน Backend ตอบ JSON ให้ frontend จัด UI/state

## Frontend Page Required Later

ต้องกลับมาทำหน้า:

```text
app-web /auth/verify-email
```

หน้านี้ต้อง:

- อ่าน `token` จาก query string
- แสดง loading state ระหว่าง verify
- call `POST /api/v1/auth/verify-email`
- แสดง success state
- แสดง expired token state
- แสดง invalid token state
- แสดง already used token state
- มีทางไป login
- ถ้า token หมดอายุ ควรมีทางไป resend verification email

## Backend Endpoint Required Later

ยังต้องทำ:

```text
POST /api/v1/auth/resend-verification-email
```

เหตุผล:

- ถ้า email ไม่ถึง
- ถ้า token หมดอายุ
- ถ้า user เปิดหน้า verify แล้วเจอ expired token

กติกาที่ควรมี:

- รับ email
- normalize email
- ไม่เปิดเผยว่า email มี account หรือไม่ถ้าไม่จำเป็น
- ส่งเฉพาะ account ที่ยัง `pending_verification`
- revoke active token เก่า
- create token ใหม่
- ส่ง email ใหม่
- rate limit ต่อ email และต่อ IP
- เขียน security event

## Login Dependency

ก่อนทำ login ให้จำไว้:

- login ควร allow เฉพาะ `user_accounts.status = active`
- account `pending_verification` ต้อง login ไม่ได้ หรือได้ response ที่บอกให้ verify email ก่อน
- login ต้องใช้ session-based auth + Redis + httpOnly cookie
- ห้ามเปลี่ยนไปใช้ JWT เป็น auth หลัก
