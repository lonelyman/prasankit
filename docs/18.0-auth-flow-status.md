# Auth Flow Status

เอกสารนี้ใช้บอกสถานะจริงของ Auth flow ว่าทำอะไรไปแล้ว อะไรยังเป็น manual/testing workaround และจุดไหนต้องกลับมาแก้เมื่อเริ่ม frontend หรือ workspace flow

## Current Status

ตอนนี้ทำ backend foundation ของ email/password auth แล้วบางส่วน:

```text
register backend done
-> send verification email done
-> verify-email backend done
-> resend verification email backend done
-> login backend done
-> session cookie + Redis session store done
-> auth session validation done
-> me backend done
-> logout backend done
-> frontend verification page not done
-> logout-all not done
```

## What Is Done

### POST /api/v1/auth/register

ทำแล้ว:

- รับ email/password
- normalize email
- validate email
- validate password ขั้นต่ำ 8 ตัวอักษร
- เช็ก email ซ้ำ
- rate limit การส่ง verification email ต่อ IP ด้วย Redis
- hash password ด้วย bcrypt
- สร้าง `user_accounts`
- สร้าง `auth_identities`
- สร้าง `auth_email_verification_tokens`
- เก็บเฉพาะ token hash ใน database
- ส่ง verification email ผ่าน SMTP จริง
- เขียน `security_events`:
  - `auth.account_registered`
  - `auth.email_verification_sent`

ผลลัพธ์ปัจจุบัน:

- account ใหม่เป็น `pending_verification`
- email มี frontend URL ตาม `MAIL_VERIFY_BASE_URL`
- link ใน email ควรเป็น frontend URL เช่น:

```text
http://localhost:3000/auth/verify-email?token=<token>
```

### POST /api/v1/auth/verify-email

ทำแล้ว:

- รับ `token`
- hash token แล้วหาใน `auth_email_verification_tokens`
- เช็ก token status เป็น `active`
- เช็ก token ยังไม่หมดอายุ
- mark token เป็น `used`
- set `auth_identities.email_verified_at`
- set `user_accounts.status = active`
- เขียน `security_events`:
  - `auth.email_verified`

ผลลัพธ์ปัจจุบัน:

- ถ้า token ถูกต้อง account เปลี่ยนเป็น `active`
- token ใช้ซ้ำไม่ได้
- token หมดอายุได้ตาม `MAIL_VERIFY_TOKEN_TTL`

### POST /api/v1/auth/resend-verification-email

ทำแล้ว:

- รับ email
- validate email
- rate limit ต่อ IP และต่อ email
- ถ้า account ไม่มีอยู่หรือ verified แล้ว ตอบ generic success
- ถ้า account ยัง `pending_verification`:
  - revoke active token เก่า
  - create token ใหม่
  - ส่ง verification email ผ่าน SMTP จริง
  - เขียน `security_events`:
    - `auth.email_verification_resent`

### POST /api/v1/auth/login

ทำแล้ว:

- รับ email/password
- normalize email
- ตรวจ password ด้วย bcrypt
- login ได้เฉพาะ email/password identity ที่ verify แล้ว
- login ได้เฉพาะ `user_accounts.status = active`
- สร้าง session token แบบ random
- hash session token ด้วย server-side `SESSION_SECRET`
- เก็บ session metadata ใน `auth_sessions`
- เก็บ session record ใน Redis
- set httpOnly cookie ตาม `SESSION_COOKIE_NAME`
- เขียน `auth_login_attempts` ทั้ง success/failure
- เขียน `security_events`:
  - `auth.login_success`
  - `auth.login_failed`

ผลลัพธ์ปัจจุบัน:

- response body ไม่ส่ง raw session token
- raw session token อยู่ใน httpOnly cookie เท่านั้น
- cookie ใช้ `COOKIE_SECURE` และ `COOKIE_SAMESITE` จาก `.env`

ยังไม่จบ flow:

- ยังไม่มี logout-all/revoke session ทุกอุปกรณ์

### GET /api/v1/auth/me

ทำแล้ว:

- อ่าน session token จาก httpOnly cookie ตาม `SESSION_COOKIE_NAME`
- hash session token ด้วย `SESSION_SECRET`
- ตรวจ session record ใน Redis
- ตรวจ session ยังไม่หมดอายุ
- โหลด `user_accounts` จาก database
- require account status `active`
- response อยู่ใต้ root key `data`

ผลลัพธ์ปัจจุบัน:

- ใช้ตรวจ session ปัจจุบันได้
- ยังคืนเฉพาะ account กลาง
- ยังไม่คืน workspace membership, tenant context, role หรือ permission

### POST /api/v1/auth/logout

ทำแล้ว:

- อ่าน session token จาก httpOnly cookie ตาม `SESSION_COOKIE_NAME`
- hash session token ด้วย `SESSION_SECRET`
- อ่าน session record จาก Redis
- update `auth_sessions.status = revoked`
- set `auth_sessions.revoked_at`
- set `auth_sessions.revoked_reason = user_logout`
- เขียน `security_events`:
  - `auth.logout`
- ลบ session record จาก Redis
- clear httpOnly cookie

ผลลัพธ์ปัจจุบัน:

- logout ปิดเฉพาะ session ปัจจุบัน
- session อื่นของ account เดียวกันยังใช้ได้จนกว่าจะ logout เอง, logout-all, หรือหมดอายุ

## What Is Temporary

ตอนนี้ยังไม่มี frontend page:

```text
/auth/verify-email
```

ดังนั้นการทดสอบตอนนี้ยังเป็น manual:

1. สมัครด้วย `POST /api/v1/auth/register`
2. เปิด email ที่ได้รับ
3. copy ค่า `token` จาก query string ใน link
4. ยิง `POST /api/v1/auth/verify-email` ด้วย curl

นี่เป็น temporary testing flow เท่านั้น ไม่ใช่ user flow สุดท้าย

## Correct Final User Flow

Flow ที่ต้องเป็นจริงเมื่อมี frontend:

```text
User opens register page
-> frontend calls POST /api/v1/auth/register
-> backend sends verification email with frontend URL
-> user clicks email link
-> frontend opens /auth/verify-email?token=...
-> frontend shows verifying state
-> frontend calls POST /api/v1/auth/verify-email
-> frontend handles success/error states
-> user continues to login or workspace setup
```

Backend ไม่ควรเป็นคน render หน้า verify email เองใน architecture ปัจจุบัน Backend ตอบ JSON ให้ frontend จัด UI/state

## Frontend Page Required Later

ต้องกลับมาทำหน้า:

```text
app-web /auth/verify-email
```

หน้านี้ต้อง:

- อ่าน `token` จาก query string
- แสดง loading state ระหว่าง verify
- call `POST /api/v1/auth/verify-email`
- แสดง success state
- แสดง expired token state
- แสดง invalid token state
- แสดง already used token state
- มีทางไป login
- ถ้า token หมดอายุ ควรมีทางไป resend verification email

## Login Dependency

สถานะหลังทำ login:

- login allow เฉพาะ `user_accounts.status = active`
- account `pending_verification` login ไม่ได้ และตอบ `EMAIL_NOT_VERIFIED`
- login ใช้ session-based auth + Redis + httpOnly cookie แล้ว
- ห้ามเปลี่ยนไปใช้ JWT เป็น auth หลัก

ขั้นถัดไปของ auth/session:

- ทำ logout-all โดย revoke sessions ทุกอุปกรณ์ของ account เดียวกัน
- ขยาย `GET /api/v1/auth/me` ในรอบ Workspace ให้คืน workspace membership/context ตามสิทธิ์
